2. Por que a complexidade é acidental

Nada aqui é regra de negócio: a única regra é "primeiro DATE dentro de BIRT" e "primeira família que liga". A duplicação não protege nada. O risco real é de divergência: no dia em que a leitura de DATE ganhar um caso de fallback (data estimada, por exemplo), PLAC fica para trás em silêncio, e a ficha passa a mostrar local de nascimento ausente só para algumas pessoas.

O que ficou de fora, e por quê A oportunidade propunha também um _casal_da_familia para substituir as quatro leituras de HUSB e WIFE. Ele foi descartado depois de medido: em _construir_indice_de_filhos o casal e os filhos saem na MESMA passada, e hop_evidence precisa só do primeiro de cada. Um helper que devolvesse os dois teria mais linhas do que as quatro que substituiria, e acrescentaria uma passada. Simplificar não é extrair por extrair.

3. A solução proposta

Uma varredura, duas constantes

def _sub_valor(people, pid, tag, sub_tag):
    """Primeiro valor do sub-registro `sub_tag`
    dentro do registro `tag`, ou None."""
    pessoa = people.get(pid)
    if not pessoa:
        return None
    for rec in pessoa.sub_records:
        if rec.tag == tag:
            for sub in rec.sub_records:
                if sub.tag == sub_tag:
                    return str(sub.value)
    return None


def _data_de(people, pid, tag):
    return _sub_valor(people, pid, tag, "DATE")


def _local_de(people, pid, tag):
    return _sub_valor(people, pid, tag, "PLAC")

A pergunta com nome

def _pais_da_familia(familia) -> set:
    """Os ids declarados como HUSB e WIFE."""
    return {ref_id(r.value) for r in familia.sub_records
            if r.tag in ("HUSB", "WIFE")}


def _familia_que_liga(families, candidatos, parent_id):
    """A primeira família de `candidatos` em que
    `parent_id` é HUSB ou WIFE."""
    for fam_id in candidatos:
        familia = families.get(fam_id)
        if familia and parent_id in _pais_da_familia(familia):
            return fam_id
    return None
